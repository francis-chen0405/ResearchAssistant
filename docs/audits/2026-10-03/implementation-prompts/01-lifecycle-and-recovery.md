## Required behavior

1. **Pre-upgrade backup.** For an existing database that needs a writable schema upgrade, acquire the same per-database process lock used by fresh-v2/live workers and history import, then re-check the schema version under the lock. Validate the source without initializing it; preserve the public read-only rejection of schemas 1–6 while using explicit recorded-version upgrade checks for recognized older writable inputs. Prompt 2 strengthens those shared preflight checks. Before the first source schema or migration-ledger write, create a private backup using SQLite’s backup API. Use a collision-resistant temporary name, close connections deterministically, verify the backup with `integrity_check` and its recorded schema version, plus structural/FK checks appropriate to that version and source-versus-copy identity checks. Record non-sensitive source identity, versions, creation time, and recovery metadata; do not include credentials or research contents in logs. Then publish it atomically under a stable, discoverable backup name. Never overwrite the source or another backup. Use a genuinely no-overwrite publish operation: ordinary rename/replace may overwrite an occupied target. Keep the verified result durable with the file/directory flushing required by the selected platform. Do not copy only the main file of a live WAL database, and do not expose a partly built copy as complete. If acquiring the lock, creating the backup, verifying it, or writing due to disk exhaustion fails, do not begin the migration. Keep a verified backup when a migration later fails or is interrupted.

   Avoid nested-lock deadlocks: make lock ownership explicit at orchestration boundaries, using a retained-lock/`lock_owned` pattern where an outer CLI, live worker, or legacy worker already holds it. Do not release a worker’s lock while any recovery, migration, or database write can still occur. Ensure cancellation during a run cannot make the database appear idle before the worker has exited its write path.

2. **Bounded retention and explicit restore.** Retain a bounded, configurable number or age of verified backups per database. Prune only after a later upgrade succeeds, never before a new verified backup exists, and never delete the last verified backup. A failed cleanup must not roll back an otherwise successful upgrade. Provide an explicit, discoverable restore workflow through a suitable existing API/CLI/UI surface. Restore only to a new, non-existing database path; never overwrite the source, current database, or user-restored data. Verify the restored copy before reporting success. Do not perform a restore or migrate an actual user database as part of this task; all end-to-end migration and restore tests must use disposable temporary databases and paths.

3. **Private imported copies.** For the application-owned default import directory and every new imported SQLite copy, enforce owner-only access on POSIX even when the folder already exists or the process umask is permissive. Create the DB securely (rather than relying on default `Path.open("xb")` mode), retain exclusive creation, and preserve current cleanup rules so a failed import removes only a file created by that import. On Windows, use or document an appropriate per-user ACL policy and add platform-guarded checks; do not claim POSIX mode bits alone protect Windows. Do not silently chmod arbitrary caller-supplied destination directories. Keep the imported DB as a usable copy, not an invisible API-only artifact: wire any added recovery/import affordance into the existing desktop experience or provide a clear supported CLI flow and user-facing result/path.

4. **Consistent database parent handling.** Make a fresh-v2 CLI run with a nested new database path behave consistently with the legacy CLI and the desktop API: either create the selected parent before opening the sidecar lock, or validate it early and give a direct, documented error. Prefer the existing legacy behavior of creating parents when the user selected the path. Use appropriately private permissions for app-owned default folders; do not unexpectedly tighten a user-selected working directory.

5. **Lock protocol for retained legacy entry points.** Default live workers, fresh-v2 CLI/direct orchestration, and imports already share the database sidecar lock. If the legacy `run_provider_pipeline`/injected legacy runner remains a supported execution path, make it participate in the same lock protocol so history import cannot mistake an active legacy writer for an idle source. Avoid acquiring the same lock twice when an outer caller owns it. If the legacy path is retired or test-only, establish that from repository call sites and documentation rather than adding unnecessary production locking.
