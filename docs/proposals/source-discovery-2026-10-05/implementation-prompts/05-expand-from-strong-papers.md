## Phase-specific task

Prerequisite: verify Phases 1–4. Add a genuinely different discovery method inside v2's existing research rounds: expand from promising, relevant papers into references, citing papers, and related work. This is not a new generic search round and must not become an unbounded citation crawler.

## 1. Select and resolve seeds conservatively

Use the typed policy and explicit seed-eligibility result. Prefer papers with direct relevance, a resolvable scholarly identity, credible observable study/review metadata, and useful substantive previews. Do not label a seed “excellent” merely because it is highly cited, appears at a prestigious domain, or supports the desired conclusion. Where no reliable seed exists, return a typed skipped outcome and continue the ordinary pipeline. There must be no extra unbudgeted model-quality call. Reuse available Scout/selection metadata and deterministic criteria; any new model-owned decision requires the full route/accounting treatment in the shared contract.

Resolve OpenAlex work IDs/DOIs using enabled configured providers only. For a web-discovered paper, use verified identifiers or a conservative exact identity match; title similarity alone cannot establish equivalence. Validate conflicting DOI/title/author/year/version information and retain ambiguity as unresolved. Public identifiers are data, not arbitrary URLs to fetch. Use fixed supported provider endpoints and the established public-URL/redirect policy for candidate source locations.

Implement a typed neighborhood capability for OpenAlex first, since its adapter already exists. Reuse the provider interface or a narrow capability protocol, with supported identity lookup, references, incoming citations, and related work backed by current official documentation: https://help.openalex.org/how-to/api-recipes/ and https://help.openalex.org/data/works/attributes/. Retain canonical work IDs, DOI, useful metadata, and documented source/PDF locations. Do not infer a verified citation relationship from an LLM suggestion or a similar title. An unsupported relationship mode is explicitly skipped, not advertised as implemented.

## 2. Plan expansion within authorized rounds

Select seeds only after the necessary current-round discovery/acquisition/preview information exists. Offer eligible expansion actions to the existing adaptive planning/Governor path for a subsequently authorized round. Expansion actions consume the existing logical provider-lane slots; each underlying identity lookup, detail batch, page, or neighbor request separately consumes applicable physical provider ceilings and cost reservation. Do not create a parallel unlimited graph quota. Model-generated action plans stay within enabled directions/providers and valid target Gap IDs.

Keep Round 2/3 query/lane caps, bounded Round-3 stopping rules, and Round-4 Governor authorization/two-lane/two-query-per-lane limits. No expansion after terminal stopping and no fifth round. A graph lookup may form one logical action with several explicitly bounded HTTP requests, like pagination, but it cannot hide unaccounted requests. If resolution exhausts the action/provider budget before neighbors can be fetched, persist the partial resolved/pending state; do not silently finish the crawl outside the round.

Use the configured limits: at most three seeds per run, one-hop expansion, at most ten unique neighbors per seed across relation types, and thirty unique expansion candidates per run, further reduced by remaining metadata, slot, provider, model, and acquisition capacity. Persist relationship priorities and deterministic tie-breaks. Batch provider detail lookups where supported and bound returned metadata/edges; do not fetch every reference before applying the cap. Track failed/used seeds and visited work/action IDs so repeats/cycles, self-references, duplicate aliases, and completed relationships do not consume work again.

## 3. Provenance, ranking, and evidence handoff

Persist the expansion plan, seed resolution, physical requests, observed relationship edges, normalized neighbors, dispositions, and partial/failure/skip results as typed hashed artifacts with stable IDs. Expanded candidates must retain parent seed/work ID, relation type, provider, actual action ID, round, lane, and target gaps. Adapt query-centric discovery readers/handoffs honestly rather than fabricating a normal query string or a first-party retrieval snapshot.

Feed expanded candidates into Phase 3's common normalization/dedup/ranking/Scout/acquisition path and Phase 4 previews. Do not create a second pipeline with looser quality gates. Expanded records can reveal different outcomes; a citation does not imply agreement or factual truth. Same-work locations/versions are not independent evidence. Original search provenance remains intact, and every ultimate snapshot/quote/admission chain must trace to the correctly owned discovery action.

Handle no configured capable provider, unresolved seed, retracted/conflicting/withdrawn work, unsupported API field, rate limit/outage, malformed graph response, empty neighborhood, partial detail lookup, cap exhaustion, cancellation, unknown response, and interrupted resume. External transport policy must be explicit; never expose provider API keys in persisted URLs.
